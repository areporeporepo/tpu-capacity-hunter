# Cross-generation TPU benchmark: v5e vs v6e

Qwen3-4B training step, measured 2026-08-14 on `soe-hpccenter`.

## Method

Identical MaxText config on every chip, so the only variable is silicon:

| Setting | Value |
|---|---|
| Model | `qwen3-4b-thinking-2507` |
| MaxText | pinned `17c7172` |
| JAX | 0.11.0 |
| Global batch | 256 |
| Sequence length | 256 (65,536 tokens per step) |
| Data | `dataset_type=synthetic`, `reuse_example_batch=true` |
| Weights | frozen, `learning_rate=0` |
| Sharding | `ici_fsdp_parallelism=1`, `ici_tensor_parallelism=<chips>` |
| Steps | 12, averaging the last 8 |

Frozen weights and synthetic data are deliberate: this measures the systems
path, not convergence, and it removes the dataset and checkpoint from the
comparison entirely (which also avoids a cross-region checkpoint pull).

Steady-state step time was stable to three decimal places on both chips, so
run-to-run noise is not a factor in these numbers.

## Results

| Metric | v5e (8 chips) | v6e (8 chips) | Ratio |
|---|---|---|---|
| Step time | 4.039 s | **1.870 s** | **2.16x** |
| TFLOP/s/device | 49.41 | 106.73 | 2.16x |
| Tokens/s/device | 2,028 | 4,382 | 2.16x |
| Total tokens/s | 16,226 | **35,052** | 2.16x |
| Spec bf16 peak/chip | ~197 TFLOPS | ~918 TFLOPS | 4.66x |
| **MFU** | **25.1%** | **11.6%** | **0.46x** |
| Zone | us-south1-a | us-central1-b | |
| Provisioning | spot | spot | |

**Validation against the prior 8-chip v5e run:** previously published 16,562
tokens/s at 25.5% MFU; measured here 16,226 tokens/s at 25.1% MFU. Agreement
within 2% means these numbers are directly comparable to the earlier study.

## Why v6e wins by only 2.16x when it has 4.66x the compute

| Ratio v6e / v5e | Value |
|---|---|
| bf16 compute | 4.66x |
| HBM bandwidth (~1640 vs ~819 GB/s) | 2.00x |
| **Measured speedup** | **2.16x** |

The measured speedup tracks **HBM bandwidth**, not compute. At sequence length
256 this workload is memory-bandwidth-bound: a chip with 4.7x the math units
can still only be fed about 2x faster. This independently reproduces the
earlier observation of 59.4% of HBM bandwidth against only 25.5% of compute
peak on v5e.

Two consequences:

1. **MFU falls as chips get faster on this workload.** MFU divides by spec
   peak, so the denominator grew 4.66x while achievable throughput grew 2.16x.
   Reporting MFU alone across generations is misleading. Report tokens/s and
   MFU together.
2. **v5e is plausibly the better value for this exact config.** If v6e costs
   more than 2.16x v5e per chip-hour, v5e wins on cost per token here. v6e only
   pays off once sequence length or batch is raised enough to become
   compute-bound.

The actionable follow-up is therefore not "get newer chips", it is "raise
sequence length". Newer silicon cannot help a workload that is not feeding it.

## v5p

Not measured. v5p was reachable on this project (quota grants exist and
requests were admitted in us-central1-a, us-east5-a and europe-west4-b) but
never held long enough to benchmark: on-demand v5p was unavailable in every
zone tried, spot v5p was preempted twice before the install finished. That
scarcity is itself a result: of the three families, v5p was the hardest to
obtain, v6e was obtainable only via spot, and v5e was the only one available at
multiple sizes.

## Caveats

- Spec peak FLOPS and HBM bandwidth are vendor figures, not measured here. The
  ratios that matter (2.16x measured vs 2.00x bandwidth) are robust to modest
  errors in those denominators, but verify them before publishing.
- 8 chips on both sides, single slice, so this says nothing about ICI or DCN
  scaling. Interconnect behaviour needs the multislice runs.
- Both nodes were spot instances, which affects availability, not performance.
