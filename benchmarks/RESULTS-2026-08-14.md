# Cross-generation TPU benchmark: v5e vs v6e vs v5p

Qwen3-4B training step, measured 2026-08-14 on `soe-hpccenter`.

## A few terms

Assumed known: TPU, HBM, MFU, FLOPs, bf16, MoE, DP/TP/FSDP, SFT, GKE, VM. Only
the ones that actually trip people up:

| Term | Meaning |
|---|---|
| ICI | Inter-Chip Interconnect: the fast fabric *inside* one slice |
| DCN | Data Center Network: the slower fabric *between* slices |
| Bytes per FLOP | HBM bandwidth divided by compute peak. The ratio that predicts MFU here |
| `A3B` / `A95B` | Active parameters per token in an MoE model, e.g. 3B active out of 30B total |
| v5e / v5p | Efficiency class vs performance class. Same generation, very different bandwidth-to-compute |
| `v5p-16` | **8 chips**, not 16. v5p counts tensorcores at 2 per chip |

**Quota is not capacity.** Quota is permission to create chips: exceeding it
returns 429 instantly and retrying cannot help. Capacity is chips physically
free: the request is accepted, then rolls back, and retrying can help.

## Method

Identical MaxText configuration on every chip, so the only variable is silicon:

| Setting | Value |
|---|---|
| Model | `qwen3-4b-thinking-2507` |
| MaxText | pinned commit `17c7172` |
| JAX | 0.11.0 |
| Global batch | 256 (128 for the v5p parity run) |
| Sequence length | 256 |
| Data | `dataset_type=synthetic`, `reuse_example_batch=true` |
| Weights | frozen, `learning_rate=0` |
| Sharding | FSDP off, TP capped at 8, remainder on the DP axis |
| Steps | 12, averaging the last 8 |

Frozen weights and synthetic data are deliberate: this measures the systems
path, not convergence, and removes the dataset and checkpoint from the
comparison entirely.

Steady-state step time was stable to three decimal places on every chip, so
run-to-run noise is not a factor.

**Tensor parallelism caps at 8.** Qwen3-4B has 8 KV heads (parameter shape
`(2560, 36, 8, 128)`), so `ici_tensor_parallelism=16` fails with a JAX
`IndivisibleError`. Sixteen-chip runs must therefore use DP2 x TP8, which is
exactly the layout the class assignment specifies.

## Results, per chip at per-device batch 32

| Metric | v5e | v6e | v5p |
|---|---|---|---|
| Chips | 8 | 8 | 4 |
| Step time | 4.039 s | 1.870 s | 1.372 s |
| TFLOP/s per chip | 49.41 | 103.7 to 106.7 | **145.4** |
| **Tokens/s per chip** | 2,028 | 4,382 | **5,969** |
| **MFU** | 25.1% | **11.6%** | **31.7%** |
| Speedup per chip vs v5e | 1.00x | 2.16x | **2.94x** |

## Results, total throughput

| Configuration | Chips | Step time | Total tokens/s |
|---|---|---|---|
| v5e, 8 chips (TP8) | 8 | 4.039 s | 16,226 |
| v6e, 8 chips (TP8) | 8 | 1.870 s | 35,052 |
| **v6e, 16 chips (DP2 x TP8)** | 16 | **0.962 s** | **68,102** |
| v5p, 4 chips (TP4) | 4 | 2.758 s | 23,763 |

**Validation:** the earlier published 8-chip v5e run gave 16,562 tokens/s at
25.5% MFU. Measured here: 16,226 tokens/s at 25.1%. Agreement within 2%, so
these numbers are comparable to that study.

## Finding 1: ICI scaling on v6e is 97%

Going from 8 to 16 v6e chips at fixed global batch (the definition of strong
scaling) took step time from 1.870 s to 0.962 s:

- Speedup: **1.943x for 2x the chips**
- **Strong-scaling efficiency: 97.1%**
- Per-chip throughput held at 4,382 then 4,256 tokens/s, a 2.9% loss

So the ICI fabric is essentially free at this scale on v6e, matching the ~100%
ICI efficiency previously measured on v5e. Interconnect is not the bottleneck
inside a slice.

## Finding 2: speedup tracks memory bandwidth, not compute

The v5e-to-v6e comparison is the cleanest one (same chip count, same per-device
batch):

| Ratio v6e / v5e | Value |
|---|---|
| bf16 compute | 4.66x |
| **HBM bandwidth** | **2.00x** |
| **Measured speedup** | **2.16x** |

v6e has 4.66x the compute yet delivered 2.16x the throughput, essentially the
bandwidth ratio. At sequence length 256 this workload is
**memory-bandwidth-bound**: a chip with 4.7x the arithmetic units can only be
fed about 2x faster. This independently reproduces the earlier observation of
59.4% of HBM bandwidth achieved against only 25.5% of compute peak.

v5p behaves the same way: 2.94x measured against a 3.38x bandwidth ratio and
only a 2.33x compute ratio. Both newer chips land near their bandwidth ratio,
not their FLOPs ratio.

## Finding 3: MFU is predicted by bytes per FLOP

Rank the chips by memory bandwidth divided by compute peak, and the MFU
ordering falls out exactly:

| Chip | HBM bandwidth | bf16 peak | **Bytes per FLOP** | **Measured MFU** |
|---|---|---|---|---|
| v5p | ~2765 GB/s | ~459 TFLOPS | **6.02** | **31.7%** |
| v5e | ~819 GB/s | ~197 TFLOPS | **4.16** | **25.1%** |
| v6e | ~1640 GB/s | ~918 TFLOPS | **1.79** | **11.6%** |

Perfect rank correlation across three chips. This is the single most useful
result here: for this workload, **a chip's MFU is set by how much bandwidth it
has per unit of compute**, not by how fast it is. v6e is the fastest chip in
absolute terms and has the worst MFU, because its compute grew far faster than
its bandwidth.

Two consequences:

1. **Never compare MFU across chip generations without saying so.** MFU divides
   by spec peak, so a bigger denominator lowers MFU even when throughput
   improves. Report tokens/s and MFU together.
2. **v5e is plausibly the best value for this exact configuration.** If v6e
   costs more than 2.16x v5e per chip-hour, v5e wins on cost per token. Newer
   silicon only pays off once sequence length or batch is large enough to become
   compute-bound.

### Correction: raising sequence length does not help

An earlier version of this file recommended raising sequence length. A sweep
measured on both chips refutes that, so the recommendation is withdrawn.

Tokens per step held at 65,536, so batch falls as sequence rises:

| Sequence | Batch/chip | v5e MFU | v6e MFU |
|---|---|---|---|
| 256 | 32 | 25.08% | 11.63% |
| 512 | 16 | 25.41% | 12.09% |
| 1024 | 8 | 25.20% | 11.83% |
| 2048 | 4 | 25.30% | 11.66% |

An 8x sequence range moves MFU by under half a point on either chip.

Why, and why this is a better result than the original claim: arithmetic
intensity depends on **tokens per weight load**, not on how those tokens are
arranged into batch by sequence. Holding tokens per step constant held intensity
constant by construction. Combined with the original batch sweep, where MFU
plateaued at 25.5% across an 8x batch range, the conclusion is that **MFU here
is pinned by the chip's bytes-per-FLOP ratio and is nearly insensitive to work
shape**. That in turn implies activation traffic under TP8 scales with token
count just as FLOPs do, so there is no batch or sequence setting that escapes it.

The remaining levers are the **sharding strategy** (FSDP versus TP, since TP8
activation traffic looks like the real cost) and the **model architecture**
(sparse MoE changes the bytes-per-token maths entirely). Not the batch and
sequence dials.

Secondary observation: at fixed TFLOP/s, longer sequences cost tokens per second
(v5e 2,028 down to 1,921; v6e 4,382 down to 4,124) because attention FLOPs grow
quadratically while token count is held fixed.

### Google's published specs say the same thing

| Per chip | v5e | v6e | Ratio |
|---|---|---|---|
| bf16 compute | 197 TFLOPs | 918 TFLOPs | **4.66x** |
| int8 | 393 TOPs | 1836 TOPs | 4.67x |
| HBM capacity | 16 GB | 32 GB | **2.0x** |
| HBM bandwidth | 800 GiBps | 1638 GBps | **~2.0x** |
| ICI bidirectional | 400 GBps | 800 GBps | **2.0x** |
| Chips per host | 8 | 8 | 1x |
| Pod size | 256 | 256 | 1x |

Every ratio is 2x except compute. Our measured 2.16x speedup tracks the memory
column. Note Google documents v5e bandwidth in GiBps and v6e in GBps, so the
bandwidth ratio is 1.9x to 2.05x depending on conversion; either way it is
nowhere near 4.66x. Sources: cloud.google.com/tpu/docs/v5e and /v6e.

## Availability, which is itself a result

| Family | On-demand | Spot | Notes |
|---|---|---|---|
| v5e | blocked in us-west4-a, quota 32/32 held by 4 peer nodes | **worked** | Spot succeeded in us-west4-a *while on-demand was exhausted*, because spot bills against a separate per-zone quota metric |
| v6e | 1 chip only (us-east5-b) | **worked at 8 and 16 chips** (us-central1-b) | Multi-chip v6e was unobtainable on-demand in every zone tried |
| v5p | unavailable in every zone tried | worked, but **preempted twice** before a run finished | Scarcest of the three |
| TPU7x (Ironwood) | **absent from this project entirely** | | Generally available in Google Cloud since 2026-04-22, but no `tpu7x` accelerator type exists in any of the project's 121 TPU zones |

Practical guidance: **use `--spot`**. It draws on a different quota bucket, so
it does not compete with the on-demand pool classmates need, and it is
substantially cheaper. The cost is preemption, so checkpoint often.

Also note Kueue's ClusterQueue on the class GKE cluster covers only
`tpu-v5e-flavor`. A v6e or v5p JobSet would stay pending forever until an
instructor adds a matching ResourceFlavor and quota.

## Caveats

- Spec peak FLOPS and HBM bandwidth are vendor figures, not measured here. The
  central claims are ratio-based and robust to modest error in those numbers,
  but verify before publishing.
- Single slice throughout. Finding 1 is ICI scaling only; nothing here measures
  DCN. That needs the multislice runs.
- v5p ran 4 chips against 8 for the others, so per-chip metrics are the valid
  comparison, not totals.
- All nodes were spot instances, which affects availability, not performance.

## Roadmap context: our bottleneck is the one Google is fixing next

Announced at Cloud Next 2026, the eighth generation splits into two chips,
both on TSMC 2 nanometre, targeted for **late 2027**:

| | TPU 8t "Sunfish" (training) | TPU 8i "Zebrafish" (inference) |
|---|---|---|
| Design partner | Broadcom | MediaTek |
| Dies | 2 compute + 1 input/output chiplet | 1 compute + 1 input/output die |
| Memory | **8 stacks of 12-high HBM3e** | 6 stacks of HBM3e |
| Bandwidth vs Ironwood | **~30% higher** | lower, cost-optimised |
| Performance | 121 exaflops FP4 per pod, per-pod compute nearly 3x Ironwood | 20 to 30% cheaper than the training part |
| Performance per dollar vs Ironwood | up to 2.7x for large-scale training | up to 80% for inference, especially low-latency large MoE |

Three things line up with the measurements above:

1. **8t's headline memory change is a bandwidth increase.** Going from 8-high to
   12-high HBM stacks for roughly 30% more bandwidth targets exactly the limit
   Finding 3 identifies. Our result that MFU is set by bytes per FLOP is the
   same conclusion Google's own roadmap encodes.
2. **The training/inference split confirms the framing.** Training and inference
   want different bandwidth-to-compute ratios, so one general-purpose chip is a
   compromise for both. 8t and 8i are that compromise being abandoned.
3. **FP4 is the compute direction**, matching what is trending publicly: the
   most popular models right now are MoE served in FP8 or NVFP4, not dense bf16.

Neither 8t nor 8i can be benchmarked today: they are late-2027 parts, and a
sweep of all 121 TPU zones on this project finds only v2, v3, v5e, v5p and v6e,
with not even the generally-available TPU7x present.

### Where that leaves this workload

Our configuration (dense 4B parameters, sequence length 256) is the *opposite*
of what gen 8 is built for. It is bandwidth-bound, so it cannot use compute
increases, and it is dense, so it cannot use the MoE-oriented inference
economics of 8i. The upgrade path that would actually help, in order:

1. **Raise sequence length.** Moves the workload toward compute-bound, which is
   where any newer chip starts paying off.
2. **Move to a sparse MoE model.** Every trending frontier model is MoE with a
   small active parameter count. MaxText already supports `qwen3-30b-a3b`,
   `qwen3.5-35b-a3b`, `kimi-k2-1t` and `deepseek4-284b`, so this is a
   `model_name` change, not a new stack.
3. **Then, and only then, newer silicon.** MoE adds expert parallelism, whose
   all-to-all traffic is far heavier and more latency-sensitive than
   data-parallel all-reduce. That is where the ICI-versus-DCN distinction stops
   being a 3.2x effect and starts being decisive.
